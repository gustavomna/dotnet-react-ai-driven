# Checklist — Generated Test

Walk this list for **each generated test file**, before it counts as coverage and before
the execution layers run. Every item is phrased so that **yes = proceed**. A single `no`
means the file is not yet coverage: fix it, then walk the list again.

A generated test that cannot fail is worse than no test, because it reports safety that
does not exist. This checklist exists to prove the test can fail.

---

## 1. Traceability

- [ ] **Does the file open with a header naming the requirement document and the specific criterion (or criteria) it covers?**
      *If no:* add it. Without the header, a future reader cannot tell whether deleting the test loses coverage of a requirement.
- [ ] **Does the header cite the check id (`CHK-NNN`) from `plan.json`?**
      *If no:* add it, so the plan, the test, and any resulting issue file all reference the same identifier.
- [ ] **Does the header name the layer and say why this layer proves the criterion?**
      *If no:* add it. The reason belongs next to the code it justifies, not only in the plan.
- [ ] **When the plan is inference-based, does the header say the criterion was inferred and from what?**
      *If no:* say so. A reader must not mistake an inferred expectation for a stated one.

Header shape used by this repository (TypeScript):

```ts
/**
 * Requirement: tasks/prd-example-health-check/prd.md
 * Criterion:   FR-7 — "On failure, a human-readable error message is shown with the
 *              HTTP status or network error." (prd.md#L38)
 * Check:       CHK-004
 * Layer:       unit — component render only; no browser or network needed.
 * Generated by qa-agent, round 001. Verified to fail against the pre-change tree.
 */
```

C# equivalent uses the same fields in an XML doc comment above the test class.

## 2. State coverage

- [ ] **For an interactive component, are the non-happy states asserted — error, loading, disabled, and empty — and not only the success path?**
      *If no:* add the missing states. Each gets its own `it`/`[Fact]`, never a single test with branching assertions.
- [ ] **Is each state driven through the component's real inputs (props, stubbed responses, user events) rather than by reaching into internals?**
      *If no:* rewrite. A test coupled to internal state passes after the component is rewritten correctly and fails after it is refactored harmlessly.
- [ ] **Are user interactions driven with `@testing-library/user-event` rather than raw `fireEvent`?**
      *If no:* switch. `user-event` exercises the real event sequence including focus, which is where accessibility regressions hide.
- [ ] **Are assertions made against user-visible output — accessible role, name, and text — rather than class names or DOM structure?**
      *If no:* switch to `getByRole` / `getByText`. Class-name assertions pass while the interface is unusable.
- [ ] **For an API surface, are the failure responses asserted — non-2xx status, malformed body, and empty payload — not only the 200 path?**
      *If no:* add them. In this repository that is `WebApplicationFactory<Program>` plus assertions on `HttpStatusCode` and the deserialized body.

## 3. Determinism

- [ ] **Is the test free of wall-clock dependence — no `Date.now()`, `new Date()`, `DateTime.Now`, and no bare `setTimeout` races?**
      *If no:* inject the clock or use the runner's fake timers (`vi.useFakeTimers()`), and restore them in teardown.
- [ ] **Is the test free of unseeded randomness — no `Math.random()`, `Guid.NewGuid()`, or faker output feeding an assertion?**
      *If no:* use fixed fixtures, or seed the generator explicitly and record the seed in the header.
- [ ] **Does the test make no calls to live third-party services, and no network calls that are not stubbed?**
      *If no:* stub them (`vi.stubGlobal("fetch", ...)`, a test `HttpMessageHandler`, or a Playwright `page.route` interception). A test that fails when the office wi-fi drops is not a quality signal.
- [ ] **Is the test independent of execution order and of other tests' leftovers — no shared mutable module state, and every stub undone in teardown?**
      *If no:* add `afterEach` cleanup (`vi.unstubAllGlobals()`, `vi.restoreAllMocks()`) or an `IAsyncLifetime` teardown.
- [ ] **Does the test avoid fixed sleeps in favour of awaiting a condition?**
      *If no:* replace `await new Promise(r => setTimeout(r, 500))` with `waitFor(...)` or a Playwright web-first assertion. Fixed sleeps are how a suite becomes flaky on a loaded CI runner.
- [ ] **Does the test pass when run alone and when run ten times in a row?**
      *If no:* it is flaky at birth. Fix it now; a flaky test is reported as `flaky` and blocks the round.

## 4. Secrets and environment

- [ ] **Are all credentials, tokens, connection strings, and base URLs read from environment variables?**
      *If no:* move them out. `process.env.QA_API_TOKEN` in TypeScript, `Environment.GetEnvironmentVariable` or `IConfiguration` in C#.
- [ ] **Does the file contain no literal secret — no key, token, password, cookie, or bearer string, not even an expired or "fake" one?**
      *If no:* remove it. Committed placeholder secrets train reviewers to ignore secret warnings.
- [ ] **When a required environment variable is missing, does the test fail with a clear message rather than silently skipping or passing?**
      *If no:* add the explicit guard and assertion.
- [ ] **Does the test avoid printing environment values into its output?**
      *If no:* remove the logging. Run logs are committed artifacts; redaction is a safety net, not a licence.

## 5. Fails for the right reason (mandatory)

- [ ] **Has the test been observed to FAIL before it is accepted as coverage?**
      *If no:* stop. Run it against the pre-change tree (`git stash`, or check out the base commit into a worktree), or temporarily invert one assertion, and watch it fail. An unverified test is not coverage.
- [ ] **Did it fail for the reason the criterion describes, rather than on a setup error, an import error, or a missing stub?**
      *If no:* the test is broken, not the code. Fix the test and re-verify.
- [ ] **Does the failure message name the expectation in words a reader can act on?**
      *If no:* add a custom message or split the assertion. `expected true to be false` sends the reader back into the source.
- [ ] **Was the temporary inversion reverted, and does the test now pass or fail purely on the behaviour under test?**
      *If no:* revert it before running the round.
- [ ] **Is the verification recorded in the test header (`Verified to fail against <ref>` or `Verified against inverted assertion`)?**
      *If no:* record it. This is the audit trail for ADR-006.

## 6. Collisions and write scope

- [ ] **Does the file avoid overwriting or rewriting a human-authored test?**
      *If no:* stop and write a sibling file instead. This rule has no exception, including when the human test looks wrong — a human test that looks wrong is an issue file, not an edit.
- [ ] **When a sibling file was created because of a collision, is the collision reported in `plan.md` and in the round summary?**
      *If no:* record it. Silent siblings become duplicated coverage nobody prunes.
- [ ] **Is the file inside a detected test directory, with a kebab-case name matching the project's suffix convention?**
      *If no:* move it. Nothing is written outside the detected test directories, `qa/`, and new sibling test files.
- [ ] **Is the file left in the working tree, unstaged and uncommitted?**
      *If no:* unstage it. `generation.autoStage` defaults to `false`; staging and committing are the developer's decision.

## 7. Accessibility tests specifically

- [ ] **Are the axe tags exactly `["wcag2a", "wcag2aa", "wcag22aa"]`?**
      *If no:* correct them. The conformance target is WCAG 2.2 AA and the tag set is fixed.
- [ ] **Does the file contain no `disableRules`, no `rules: { x: { enabled: false } }`, and no broad `exclude()` of `html`, `body`, `#root`, or `*`?**
      *If no:* remove them. Rule disabling is rejected outright; a third-party subtree exclusion requires a recorded suppression with `scope: "third-party"`.
- [ ] **Does the scan cover the component's interactive states — error, loading, disabled, empty, open — and not only its initial render?**
      *If no:* add a scan per state. Most real violations appear after interaction.
- [ ] **Do keyboard-reachability and focus-order assertions run alongside the axe scan?**
      *If no:* add them. Automated rule engines do not cover Tab reachability, visible focus, keyboard traps, or focus return from a closed modal.
- [ ] **Does the test avoid claiming compliance in its name or comments?**
      *If no:* rephrase. Automated scanning catches roughly a third to a half of real issues; the wording must say what was proven, not what is compliant.

---

## Accept gate

A generated test counts as coverage only when every box above is ticked **and** the file
has been observed failing for the right reason at least once. Record that observation in
the header. Then run the round:

```bash
python3 .agents/skills/qa-agent/scripts/qa.py exec --round <N> --stack <stack.json> --scope <scope.json> --plan qa/rounds/<NNN>/plan.json
```
